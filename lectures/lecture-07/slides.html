RDBMS — Реляційні бази даних

Принципи

  • Таблиці з фіксованою схемою
  • SQL — стандартна мова запитів
  • Зв'язки між таблицями через JOIN
  • ACID-транзакції
  • Constraints: PK, FK, UNIQUE, CHECK
  • Нормалізація: дані без дублювання

Популярні рушії

  • PostgreSQL — потужний, відкритий
  • MySQL — широко розповсюджений
  • Oracle — enterprise
  • SQL Server — Microsoft
  • MariaDB — fork MySQL
AWS: RDS підтримує всі ці рушії

NoSQL — "Not Only SQL"

Принципи

  • Гнучка або відсутня схема (schema-less)
  • Горизонтальне масштабування — основна мета
  • Зазвичай жертвує ACID заради продуктивності
  • Оптимізовані для конкретного паттерну доступу
  • Денормалізація даних для швидкості

Коли NoSQL?

  • Мільйони запитів/сек
  • Структура даних змінюється часто
  • Дані природньо ієрархічні (JSON)
  • Глобальний розподіл обов'язковий
  • Eventual consistency — прийнятна
NoSQL ≠ "без SQL". Це про горизонтальне масштабування та гнучкість схеми.

NoSQL тип 4: Graph

Структура

-- Cypher (Neo4j query language)
-- Хто є другами друзів Аліси?
MATCH (alice:Person {name:"Alice"})
      -[:FRIEND]->(:Person)
      -[:FRIEND]->(fof:Person)
WHERE fof.name <> "Alice"
RETURN DISTINCT fof.name

-- "Знайти шахрайські транзакції за 3 кроки"
MATCH p=(a)-[:TRANSFER*1..3]->(b)
WHERE b.flagged = true
RETURN p

Характеристики

ACID — Гарантії транзакцій

Транзакція — набір операцій, що виконуються як єдине ціле (все або нічого).

A — Atomicity

Все або нічого.
Якщо будь-який крок завершився з помилкою — весь блок відкочується.

C — Consistency

Дані завжди задовольняють усі правила (constraints, FK, CHECK).
Перехід між двома валідними станами.

I — Isolation

Паралельні транзакції не "бачать" незафіксованих змін одна одної.

D — Durability

Після COMMIT — дані збережені назавжди, навіть після збою сервера. Реалізується через WAL (Write-Ahead Log).
13 / 45

A — Atomicity: Все або нічого

Приклад: банківський переказ

BEGIN;
  -- Крок 1: зняти з рахунку A
  UPDATE accounts
  SET balance = balance - 500
  WHERE id = 1;

  -- Крок 2: покласти на рахунок B
  UPDATE accounts
  SET balance = balance + 500
  WHERE id = 2;

  -- Якщо збій між кроком 1 і 2 →
  -- ROLLBACK автоматично!
COMMIT;

Без Atomicity

❌ Проблема

Крок 1 виконався (гроші знято),
сервер впав до кроку 2 →
гроші зникли зі системи!

✅ З Atomicity

Збій → ROLLBACK → рахунок A не змінився. Система залишається в консистентному стані.
14 / 45

C — Consistency: Дані завжди валідні

-- Правило: balance >= 0
ALTER TABLE accounts
  ADD CONSTRAINT chk_balance
  CHECK (balance >= 0);

-- Спроба порушити правило:
BEGIN;
  UPDATE accounts
  SET balance = balance - 1000
  WHERE id = 1;
  -- balance: 200 - 1000 = -800
  -- ПОРУШЕННЯ CHECK!
-- → Транзакція відхиляється
-- → balance залишається 200
ROLLBACK; -- автоматично

Що забезпечує Consistency

  • PK / UNIQUE — унікальність
  • FK — посилальна цілісність
  • CHECK — бізнес-правила
  • NOT NULL — обов'язкові поля
  • Triggers — складна логіка
Consistency в ACID — це про правила бази даних,
не про розподілену консистентність (CAP)!

I — Isolation: Рівні ізоляції

Чим вищий рівень ізоляції — тим менше аномалій, але більший lock-contention.

Рівень ізоляції Dirty Read Non-Repeatable Read Phantom Read Продуктивність
Read Uncommitted можливий можливий можливий 🟢 Найвища
Read Committed (default PG) захист можливий можливий 🟡 Висока
Repeatable Read (default MySQL) захист захист можливий 🟠 Середня
Serializable захист захист захист 🔴 Найнижча
Dirty Read — читання незафіксованих даних  |  Non-Repeatable — рядок змінився між двома reads  |  Phantom — нові рядки з'явились між reads

D — Durability: Збережено назавжди

WAL — Write-Ahead Log

Послідовність:
1. App → COMMIT
2. DB записує транзакцію у WAL (на диск)
3. DB відповідає "OK" клієнту
4. (Пізніше) Дані переносяться у data files

Якщо сервер впав після кроку 2:
  → При restart: відновлення з WAL
  → Дані не втрачені ✅

Якщо сервер впав до кроку 2:
  → Транзакція не підтверджена
  → Відповідь не отримана клієнтом
  → Дані не збережені (atomicity)

В AWS

  • RDS Multi-AZ: синхронна реплікація перед підтвердженням
  • Aurora: 6 копій у 3 AZ — запис після 4/6 підтвердження
  • DynamoDB: 3 AZ реплікація автоматично
Durability ≠ Backup!
Backup захищає від логічних помилок (видалення даних).
Durability захищає від апаратних збоїв.

ACID — Повний приклад: переказ грошей

-- Стан: Аліса: 1000 грн, Боб: 300 грн

BEGIN;

  -- A (Atomicity): обидві операції або обидві ні
  UPDATE accounts SET balance = balance - 500
  WHERE id = 'alice';          -- Alice: 1000 → 500

  UPDATE accounts SET balance = balance + 500
  WHERE id = 'bob';            -- Bob:    300 → 800

  -- C (Consistency): перевірка CHECK balance >= 0
  -- I (Isolation): інші транзакції не бачать
  --                проміжних значень

COMMIT;
-- D (Durability): WAL → на диск → OK клієнту

-- Результат: Alice=500, Bob=800, сума=1300 ✅

Якщо збій між UPDATE 1 і UPDATE 2:

❌ Без ACID

Alice: 500 (знято), Bob: 300 (не додано)
500 грн зникли зі системи!

✅ З ACID (Atomicity)

ROLLBACK → Alice: 1000, Bob: 300
Система залишається в консистентному стані.
Клієнт отримує помилку і може спробувати знову.

BASE — Модель NoSQL-систем

B — Basically Available

Система завжди відповідає на запити,
навіть якщо деякі вузли недоступні.
Може повернути часткові або застарілі дані.

S — Soft state

Стан системи може змінюватись навіть без нових записів.
Реплікація "в процесі" — дані на різних вузлах тимчасово різні.

E — Eventually consistent

З часом усі репліки синхронізуються і повернуть однакові дані.
"З часом" = зазвичай мілісекунди–секунди.
"Ми гарантуємо відповідь, але не гарантуємо, що вона містить найсвіжіші дані"

BASE = компроміс між консистентністю та доступністю на користь доступності та масштабованості.

Eventually Consistent — як це виглядає

Сценарій: користувач змінює аватар у соцмережі

t=0ms  Користувач завантажує новий аватар
t=1ms  Запис у Primary Region (US-East) ✅
t=1ms  Відповідь клієнту "успішно" ✅

-- Реплікація відбувається асинхронно --

t=50ms Запит з Europe → EU-replica (стара версія!)
       Відображається старий аватар 😕

t=200ms EU-replica отримала оновлення
t=200ms+ Усі бачать новий аватар ✅

→ "Eventually consistent" = 200ms в даному випадку

Коли прийнятно?

✅ Прийнятно

  • Соцмережі (аватар, пости)
  • Кількість лайків
  • Каталог товарів
  • Статистика перегляду

❌ Неприйнятно

  • Банківські перекази
  • Медичні записи
  • Складські залишки (ecommerce)
  • Бронювання квитків

CAP теорема (Брюер, 2000)

Розподілена система не може одночасно гарантувати всі три:

C — Consistency

Усі вузли бачать однакові дані в один момент часу.

A — Availability

Кожен запит отримує відповідь (успіх або помилка).

P — Partition tolerance

Система продовжує працювати при мережевому розділенні (network partition).
P (Partition tolerance) є обов'язковим у будь-якій розподіленій системі.
Тому реальний вибір: C або A при network partition.

DB як Bottleneck

Типові симптоми

  • API latency > 500 мс
  • CPU на DB-сервері > 80%
  • Черга запитів до БД зростає
  • "Too many connections" помилка
  • Disk I/O = 100%
  • Replication lag зростає

Основні причини

Read-heavy: 95% трафіку — читання, один Primary перевантажений
Write-heavy: мільйони записів/сек, один вузол не справляється
Connection exhaustion: connection pool вичерпано
Slow queries: Full Table Scan, відсутні індекси, N+1
БД — найчастіший вузьке місце у веб-застосунках. Моніторинг обов'язковий.

Read-heavy Bottleneck

Проблема: 95% запитів — читання
          Primary DB перевантажений

 App Servers (×10)
      │
      ▼
  Primary DB ← writes
  (CPU 95%) ← reads (всі 10 серверів!)

Рішення:

 App Servers (×10)
   │reads        │writes
   ▼             ▼
Read Replica   Primary DB
(×3 шт)       (CPU 20%)
   ▲
Cache (Redis)
(cache hit → не йде до DB)

Інструменти

Read Replicas

Читання розподіляється на репліки.
Primary — тільки записи.
AWS Aurora: до 15 реплік.

Caching (Redis/ElastiCache)

Cache hit → відповідь за мікросекунди.
Cache miss → DB → зберегти в cache.
TTL контролює свіжість даних.

Write-heavy Bottleneck

Проблема: мільйони подій/сек (IoT, аналітика)
          один PRIMARY вузол не справляється

Рішення 1: Sharding
  user_id % 3 = 0  → DB Shard 0
  user_id % 3 = 1  → DB Shard 1
  user_id % 3 = 2  → DB Shard 2

Рішення 2: NoSQL (Cassandra/DynamoDB)
  Оптимізовані для write-heavy за дизайном
  Auto-sharding по partition key

Рішення 3: Async writes через queue
  App → Kafka → Consumer → DB
  (буферизація та батч-вставка)

Slow Queries — Виявлення та вирішення

Як виявити

-- EXPLAIN ANALYZE (PostgreSQL)
EXPLAIN ANALYZE
SELECT * FROM orders
WHERE customer_email = 'user@example.com';

-- Seq Scan (BAD):
-- Seq Scan on orders
--   (cost=0.00..185432.00 rows=1)
--   actual time=2341.209..2341.211 rows=1
--   Buffers: shared hit=85321

-- Index Scan (GOOD):
-- Index Scan on idx_orders_email
--   (cost=0.43..8.45 rows=1)
--   actual time=0.112..0.113 rows=1
--   Buffers: shared hit=4

Вирішення

-- Додати індекс
CREATE INDEX CONCURRENTLY
  idx_orders_email
  ON orders(customer_email);

-- Складений індекс (query має відповідати)
CREATE INDEX idx_orders_user_date
  ON orders(user_id, created_at DESC);

-- Частковий індекс (тільки активні)
CREATE INDEX idx_active_orders
  ON orders(created_at)
  WHERE status = 'active';

Sharding — Горизонтальне партиціювання

Ідея: розбити дані між кількома вузлами

Shard Key: user_id

user_id % 4 = 0  → Shard 0 (DB node 0)
user_id % 4 = 1  → Shard 1 (DB node 1)
user_id % 4 = 2  → Shard 2 (DB node 2)
user_id % 4 = 3  → Shard 3 (DB node 3)

Запит від user_id=42:
  42 % 4 = 2 → Shard 2 ✅

Cross-shard query (ПРОБЛЕМА):
  SELECT COUNT(*) FROM orders
  -- Треба питати всі 4 шарди й агрегувати 😱

Виклики шардингу

  • ❌ Cross-shard JOINs — складні або неможливі
  • ❌ Hot shard — нерівномірний розподіл
  • ❌ Re-sharding при зростанні — болісно
  • ❌ Транзакції між шардами — дуже складно
Порада: спочатку вертикальне масштабування та Read Replicas. Шардинг — крайній захід для RDBMS. DynamoDB / Cassandra шардують автоматично.

Caching — Паттерни кешування

Cache-Aside (Lazy Loading)

App → Cache?
  HIT → return
  MISS → DB → Cache → return
✅ Просто, cache тільки те що читають
❌ Cache miss = 2 запити

Write-Through

App → Cache → DB
(синхронно)
✅ Cache завжди свіжий
❌ Кожен запис = затримка

Write-Behind (Write-Back)

App → Cache
(async) Cache → DB
✅ Швидкий запис
❌ Ризик втрати даних
TTL (Time-To-Live): ключова настройка — час, після якого кеш-запис видаляється автоматично.
Короткий TTL → свіжі дані, більше навантаження на DB. Довгий TTL → stale дані, менше навантаження.

Connection Pooling — як це працює

БЕЗ ПУЛУ (кожен запит = нове з'єднання):
  Request → [TCP handshake] → [Auth] → [Query] → [Close]
  Час на з'єднання: 20–100 мс (!)
  При 1000 req/s → 1000 open connections → crash

З ПУЛОМ:
  ┌─ Pool Manager ─────────────────────┐
  │  conn-1 ○ (idle)                   │
  │  conn-2 ● (busy: request #42)      │
  │  conn-3 ○ (idle)                   │
  │  conn-4 ● (busy: request #43)      │
  │  conn-5 ○ (idle)                   │
  └────────────────────────────────────┘
  Request → Pool → (очікує вільне з'єднання) → Query
  Час: 0.1 мс (немає handshake)

AWS RDS Proxy

  • Fully managed, serverless
  • Multiplexing: 1000 клієнтів → 10 DB connections
  • Failover прозорий для клієнтів
  • IAM + Secrets Manager integration
  • Підтримує: MySQL, PostgreSQL, MariaDB, Aurora
Особливо важливо для Lambda → RDS: кожен Lambda invocation без proxy = нове з'єднання!

Anti-patterns баз даних

Anti-pattern — поширене "рішення", яке насправді створює нові проблеми або є неефективним.

Топ-5 DB anti-patterns

  1. 🐌 N+1 Query — N зайвих запитів замість одного JOIN
  2. 🔍 Відсутність індексів — Full Table Scan на мільйонах рядків
  3. 🧟 God Table — одна таблиця для всього
  4. 🎯 One DB for Everything — OLTP + Analytics + Cache разом
  5. 🚪 No Connection Pooling — нове з'єднання на кожен запит

Також варто знати

  • SELECT * замість конкретних стовпців
  • Зберігання файлів у БД (BLOB)
  • Без обмежень (constraints) — логіка тільки в app
  • Без backups або без тестування відновлення
  • Занадто рання оптимізація — шардинг без потреби

Anti-pattern: N+1 Query

❌ Проблема (N+1)

# 1 запит: отримати список замовлень
orders = db.query(
    "SELECT * FROM orders LIMIT 100"
)  # → 100 рядків

# 100 запитів: для кожного замовлення
for order in orders:
    user = db.query(
        f"SELECT * FROM users "
        f"WHERE id={order.user_id}"
    )
    print(f"{user.name}: {order.total}")

# Разом: 1 + 100 = 101 запит 😱
# При 1000 замовлень → 1001 запит

✅ Рішення (JOIN)

# 1 запит замість 101
orders = db.query("""
    SELECT o.id, o.total,
           u.name, u.email
    FROM orders o
    JOIN users u ON u.id = o.user_id
    LIMIT 100
""")

for order in orders:
    print(f"{order.name}: {order.total}")

# Або Eager Loading в ORM:
orders = Order.query\
    .options(joinedload(Order.user))\
    .limit(100).all()

Anti-pattern: Відсутність індексів

-- Таблиця: 50 млн рядків

-- ❌ БЕЗ ІНДЕКСУ → Full Table Scan
EXPLAIN ANALYZE
SELECT * FROM events
WHERE user_id = 42;

-- Seq Scan on events
--   (rows=50000000)
--   actual time=8234 ms  ← 8 секунд!
--   Buffers: shared read=652174

-- ✅ З ІНДЕКСОМ
CREATE INDEX CONCURRENTLY
  idx_events_user_id
  ON events(user_id);

EXPLAIN ANALYZE
SELECT * FROM events
WHERE user_id = 42;

-- Index Scan using idx_events_user_id
--   actual time=1.234 ms  ← 1 мілісекунда!
--   Buffers: shared hit=7

Anti-pattern: God Table

❌ Проблема

-- "Одна таблиця для всього"
CREATE TABLE entities (
  id       INT,
  type     VARCHAR,  -- 'user','product','order'
  field1   VARCHAR,  -- ім'я / назва / статус
  field2   VARCHAR,  -- email / ціна / дата
  field3   VARCHAR,  -- телефон / категорія / ...
  ...
  field50  VARCHAR,
  data     JSON  -- "all the rest"
);

-- 80% стовпців = NULL для кожного типу
-- Неможливо додати FK constraint
-- Неможливо нормально індексувати

✅ Рішення: нормалізація

-- Окремі таблиці для кожного типу

CREATE TABLE users (
  id    INT PRIMARY KEY,
  email VARCHAR UNIQUE NOT NULL,
  phone VARCHAR
);

CREATE TABLE products (
  id       INT PRIMARY KEY,
  name     VARCHAR NOT NULL,
  price    DECIMAL(10,2) CHECK (price > 0),
  category_id INT REFERENCES categories(id)
);

CREATE TABLE orders (
  id         INT PRIMARY KEY,
  user_id    INT REFERENCES users(id),
  created_at TIMESTAMP DEFAULT now()
);

Одна PostgreSQL для всього:

  OLAP (аналітика)      ─┤→ Одна DB

  Затримка для користувачів!

OLTP → RDS / Aurora

Транзакції, оновлення, ACID

Analytics (OLAP) → Redshift / Athena

Аналітичні запити, агрегації, звіти

Sessions / Cache → ElastiCache (Redis)

Sub-ms reads, TTL, pub/sub

Full-text Search → OpenSearch

Anti-pattern: No Connection Pooling

# ❌ ПОГАНО: нове з'єднання на кожен запит
# (типова помилка в Lambda/serverless)

def lambda_handler(event, context):
    conn = psycopg2.connect(
        host="my-rds.xxx.us-east-1.rds.amazonaws.com",
        database="mydb",
        user="admin",
        password="secret"
    )  # ← TCP + Auth = 50-100ms КОЖЕН РАЗ!

    cur = conn.cursor()
    cur.execute("SELECT ...")
    results = cur.fetchall()
    conn.close()  # ← з'єднання знищується
    return results

# 1000 одночасних Lambda → 1000 connections
# FATAL: remaining connection slots reserved

✅ Рішення

# Варіант 1: AWS RDS Proxy (рекомендовано)
# Просто змінити host на RDS Proxy endpoint:
conn = psycopg2.connect(
    host="my-proxy.proxy-xxx.rds.amazonaws.com",
    ...
)
# RDS Proxy мультиплексує з'єднання

# Варіант 2: connection pool в коді
# (для EC2 / ECS / не-serverless)
from psycopg2 import pool
connection_pool = pool.SimpleConnectionPool(
    minconn=2, maxconn=10, ...
)
conn = connection_pool.getconn()
# ... use conn ...
connection_pool.putconn(conn)  # повертаємо

Ключові висновки

  1. RDBMS = ACID + SQL + вертикальне масштабування → фінанси, ERP
  2. NoSQL = BASE + гнучкість + горизонтальне масштабування → scale, IoT
  3. CAP: при network partition обирай C або A. P — обов'язкове.
  4. Read-heavy → Read Replicas + Cache (ElastiCache)
  5. Write-heavy → Sharding або NoSQL (DynamoDB/Cassandra)
  6. Connection bottleneck → Connection Pool (RDS Proxy)
  7. Slow query → EXPLAIN ANALYZE → Indexes
  8. Уникай: N+1, God Table, One DB for Everything

AWS Cheat Sheet

  • RDS / Aurora → SQL, ACID, OLTP
  • DynamoDB → serverless NoSQL, scale
  • ElastiCache → кеш, сесії, pub/sub
  • Redshift → аналітика (OLAP)
