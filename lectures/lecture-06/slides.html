S3 Versioning


Без versioning:
  PUT logo.png  →  перезаписує попередній (дані втрачені)

З versioning:
  PUT logo.png  → VersionId: "abc123"  (v1)
  PUT logo.png  → VersionId: "def456"  (v2)
  PUT logo.png  → VersionId: "ghi789"  (v3, current)

  GET logo.png                     → v3 (latest)
  GET logo.png?versionId=abc123    → v1
  DELETE logo.png                  → delete marker (не видаляє!)
  DELETE logo.png?versionId=abc123 → видаляє v1 назавжди

✅ Захист від

  • Випадкового видалення
  • Людської помилки
  • Ransomware
  • Пошкодження даних

⚠️ Пам'ятати

  • Всі версії = більше storage
  • Lifecycle для старих версій
  • MFA Delete для extra protection

S3 Replication

🌍 Cross-Region Replication (CRR)

  • Різні AWS регіони
  • DR та disaster recovery
  • Latency reduction для global users
  • Compliance (дублювання)

📍 Same-Region Replication (SRR)

  • Один AWS регіон
  • Агрегація логів в один bucket
  • Тест/dev копія production даних
  • Account-to-account copy

Вимоги для реплікації:
  ✅ Versioning увімкнено на source і destination
  ✅ IAM роль з відповідними дозволами
  ✅ Шифрування? → Треба дозвіл на KMS
  ⚠️ Вже існуючі об'єкти НЕ реплікуються автоматично
     (потрібен S3 Batch Replication)

S3 Presigned URLs


# Генерація Presigned URL (Python / boto3)
import boto3

s3 = boto3.client('s3')

# Дозволити ЗАВАНТАЖЕННЯ файлу (GET)
url = s3.generate_presigned_url(
    'get_object',
    Params={'Bucket': 'my-bucket', 'Key': 'report.pdf'},
    ExpiresIn=3600   # 1 година
)
# → https://my-bucket.s3.amazonaws.com/report.pdf?X-Amz-Signature=...

# Дозволити ВИВАНТАЖЕННЯ файлу (PUT)
url = s3.generate_presigned_url(
    'put_object',
    Params={'Bucket': 'my-bucket', 'Key': 'upload/file.csv'},
    ExpiresIn=300    # 5 хвилин
)
💡 Presigned URLs: тимчасовий доступ без AWS credentials. Ідеально для file upload із frontend або sharing приватних файлів.

EBS Snapshots


Інкрементальна модель:

  Snapshot 1 (повний):    ████████████████████  20 GB
  Snapshot 2 (інкрем.):   ████                   3 GB  (зміни після snap 1)
  Snapshot 3 (інкрем.):   ██                     1 GB  (зміни після snap 2)
  ─────────────────────────────────────────────────────
  Всього збережено: 24 GB    (не 60 GB!)

Snapshot workflow


# Створити snapshot
aws ec2 create-snapshot \
  --volume-id vol-0a1b2c3d \
  --description "Pre-deploy backup"

# Відновити новий volume
aws ec2 create-volume \
  --snapshot-id snap-0a1b2c3d \
  --availability-zone us-east-1a

Можливості

  • Копіювання між regions
  • Основа для AMI
  • Encryption при відновленні
  • Amazon Data Lifecycle Manager (автоматизація)

EBS Performance Optimization

Проблеми

  • I/O bottleneck: EC2 instance може мати більший throughput, ніж EBS
  • IOPS limit: gp2 = 3 IOPS/GB (max 16k)
  • Multi-attach: тільки io1/io2, обмежено

Оптимізація

  • gp3 незалежно налаштовує IOPS і throughput
  • RAID 0: кілька EBS volumes для більшого throughput
  • EBS Optimized instances: виділений bandwidth
  • Nitro instances: менше overhead

# Збільшити IOPS без downtime (gp3)
aws ec2 modify-volume \
  --volume-id vol-0a1b2c3d \
  --volume-type gp3 \
  --iops 6000 \
  --throughput 300
💡 EBS модифікації можна робити без зупинки EC2 (Elastic Volumes)

Eventual vs Strong Consistency


Strong Consistency (S3 з 2020):
  PUT s3://bucket/file.txt (version 2)
  GET s3://bucket/file.txt → завжди version 2 ✅

Eventual Consistency (старий S3, DynamoDB default):
  PUT item {id: 1, stock: 0}      → записано в node-A
  GET item {id: 1}                → може повернути stock: 5 (старе!)
                                    поки реплікація не завершена

DynamoDB: можна обрати
  читання = EventualConsistencyRead  (дешевше)
  читання = StrongConsistencyRead    (2x вартість)
💡 Практика: Для банківських транзакцій → Strong. Для лічильників переглядів → Eventual достатньо.

S3 Security: захист даних

Рівні захисту (ешелонована оборона):

  1. Block Public Access — завжди увімкнений за замовчуванням (2023+)
  2. Bucket Policy — resource-based policy (хто, що, звідки)
  3. IAM Policy — identity-based (який IAM principal може що робити)
  4. ACL (застарілий) — не рекомендується для нових bucket
  5. Encryption at rest — SSE-S3, SSE-KMS, SSE-C
  6. Encryption in transit — HTTPS (TLS 1.2+)
  7. S3 Object Lock — WORM захист від видалення/зміни
💡 Якщо Bucket Policy і IAM Policy конфліктують → застосовується більш обмежена политика (explicit Deny перемагає)

  • ⚠️ Не завершені multipart uploads = вартість! Додайте Lifecycle rule для cleanup

Anti-Patterns: Що НЕ робити

❌ S3 помилки

  • Публічний bucket без потреби
  • Секрети / credentials в S3
  • Один bucket prod+dev+test
  • Не версіонувати критичні дані
  • Ігнорувати lifecycle (= марні гроші)
  • Не завершені multipart uploads
  • S3 замість EBS для DB

❌ EBS / EFS помилки

  • gp2 в 2024 (є gp3!)
  • Unused EBS volumes (платите за повітря)
  • Немає snapshot schedule
  • EBS без шифрування для PII
  • EFS для DB workloads (висока latency)
  • One AZ EFS для критичних даних
  • Snapshot накопичення без cleanup

Ключові висновки

  1. Storage = архітектурне рішення
    Object → S3, Block → EBS, File → EFS
  2. Автоматизуй lifecycle
    Hot → Warm → Cold → Archive → Delete
  3. Backup ≠ Archive
    Різні цілі, RPO/RTO, інструменти
  4. CAP: P завжди є в мережі
    Обирай C або A залежно від задачі
  1. GDPR: дані в правильному region + encryption
    eu-central-1 для EU даних
  2. Security by default
    Block Public Access, SSE-KMS, HTTPS only
  3. Моніторинг і оптимізація
    Storage Lens, CloudWatch, cleanup orphaned resources
  4. Event-driven storage
    S3 Events → Lambda → автоматизація
