Гіпервізори: що це?

Hypervisor — програмне забезпечення, що дозволяє запускати кілька ОС на одному фізичному сервері.

┌─────────────────────────────────────┐ │ VM 1 │ VM 2 │ VM 3 │ │ Linux │ Windows │ Linux │ ├─────────────────────────────────────┤ │ Hypervisor │ ├─────────────────────────────────────┤ │ Physical Hardware │ └─────────────────────────────────────┘
🔑 Гіпервізор дозволяє ізолювати VM одна від одної та ефективно використовувати фізичне залізо.

✅ Переваги Nitro

  • I/O на dedicated hardware → менше overhead
  • Краща ізоляція між tenants
  • Hardware root of trust (безпека)

  • Nitro Security Chip — апаратна безпека
  • Nitro Hypervisor — тонкий шар VM

Файлова система Linux

/ ├── etc/ ← конфігурації ├── var/ ← змінні дані (logs, db) │ └── log/ ← логи ├── home/ ← домашні директорії ├── tmp/ ← тимчасові файли ├── usr/ ← програми │ └── bin/ ← бінарники ├── opt/ ← стороннє ПО └── proc/ ← інфо про процеси (virtual)

📁 Ключові директорії

  • /etc/ — конфіги nginx, sshd, systemd
  • /var/log/ — всі системні логи
  • /tmp/ — очищається при перезавантаженні
  • /proc/ — live інфо про процеси
⚠️ Ніколи не зберігайте важливі дані у /tmp/!
🐧 Linux

systemd — серце Linux сервера

┌─────────────────────────────────────┐ │ systemd │ │ (PID 1, init system) │ ├───────────┬─────────────┬───────────┤ │ Services │ Sockets │ Timers │ │ (nginx, │ (systemd- │ (cron- │ │ sshd..) │ journald) │ like) │ └───────────┴─────────────┴───────────┘

⚙️ Що робить systemd

  • PID 1 — перший процес після ядра
  • Запускає всі сервіси при старті
  • Відстежує залежності між сервісами
  • Централізований збір логів (journald)

📄 Unit файли

  • /etc/systemd/system/ — кастомні
  • /usr/lib/systemd/system/ — системні
  • Типи: .service, .socket, .timer

systemctl — управління сервісами

# Запустити сервіс sudo systemctl start nginx # Зупинити сервіс sudo systemctl stop nginx # Перезапустити sudo systemctl restart nginx # Авто-запуск при завантаженні sudo systemctl enable nginx # Статус sudo systemctl status nginx # Список всіх сервісів sudo systemctl list-units --type=service
💡 enable ≠ start: enable — автозапуск при boot, start — запуск зараз.

Immutable vs Mutable Infrastructure

❌ MUTABLE (старий підхід)

  • Server існує давно
  • Update / patch in-place
  • Config drift 😱
  • "Snowflake server" 🦄
  • Важко відтворити стан

✅ IMMUTABLE (сучасний)

  • Server = одноразовий
  • Новий AMI → New server
  • Tear down old server ✅
  • Reproducible завжди
  • Git-friendly
🐄 Cattle not Pets: сервери як худоба, не як домашні тварини

Stateless Systems

12-Factor App — фактор 6: Processes

❌ Stateful (погано)

  • Request 1 → Server A
  • Зберігає session в пам'яті
  • Request 2 → Server B
  • Не знає про Request 1 😱
  • Неможливо масштабувати

✅ Stateless (добре)

  • Request 1 → Server A
  • Зберігає session в Redis
  • Request 2 → Server B
  • Читає session з Redis ✅
  • Горизонтальне масштабування
💾 Стан зберігається ЗОВНІ: Sessions → Redis/DynamoDB · Files → S3 · Database → RDS

  • Network-attached блоковий диск

EC2 Placement Groups

⚡ Cluster

  • Всі EC2 в одній AZ
  • Низька затримка мережі
  • Висока пропускна здатність
  • Use: HPC, big data
  • ❌ Ризик: одна AZ

📦 Partition

  • Групи на різних rack'ах
  • До 7 партицій на AZ
  • Ізоляція від hardware failures
  • Use: Kafka, Cassandra, HDFS
  • ✅ Баланс між performance та HA

🔀 Spread

  • Кожен EC2 на окремому rack
  • До 7 EC2 на AZ
  • Максимальна ізоляція
  • Use: критичні сервіси
  • ✅ Найвища доступність

Auto Scaling Policies

🎯 Target Tracking Scaling

  • Підтримувати метрику на заданому рівні
  • CPU = 70% → додати/прибрати інстанси
  • Найпростіший у налаштуванні
  • Use: типові web applications

📊 Step Scaling

  • Різні кроки для різних порогів
  • CPU 70-80% → +1 instance
  • CPU 80-90% → +2 instances
  • CPU >90% → +4 instances

📅 Scheduled Scaling

  • Заздалегідь відомий патерн навантаження
  • Пн-Пт 9:00 → scale out до 10
  • Пн-Пт 18:00 → scale in до 2
  • Use: B2B, офісні додатки

🤖 Predictive Scaling

  • ML-аналіз історичних даних
  • Proactive масштабування
  • Уникає cold start проблем
  • Use: periodical workloads
