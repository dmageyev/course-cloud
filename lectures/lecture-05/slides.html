Що таке обчислювальний ресурс?

💻 CPU

  • vCPU = нитка гіпервізора
  • ARM vs x86
  • Clock speed
  • Core count

🧠 RAM

  • Оперативна пам'ять
  • GB / TiB
  • Memory-optimized
  • ECC (cloud)

🌐 Network

  • Bandwidth (Gbps)
  • Enhanced Networking
  • SR-IOV
  • ENA driver

Bare metal server → завжди 100% CPU/RAM
Cloud instance   → shared host, allocated vCPU + RAM + Network
Serverless       → CPU/RAM on-demand, duration billing
💡 У хмарі "сервер" — це абстракція над фізичним залізом. Ви орендуєте ресурси, а не машину.

Virtual Machines: переваги та обмеження

✅ Переваги

  • Повна ізоляція (kernel рівень)
  • Будь-яка ОС (Windows, Linux, FreeBSD)
  • Snapshot / live migration
  • Зрілі інструменти (VMware, vSphere)
  • Відомий security model
  • Ліцензування per-VM

⚠️ Обмеження

  • Повна ОС = gigabytes RAM overhead
  • Boot time: секунди–хвилини
  • Щільність: десятки VM / host
  • Image розмір: GB
  • Resource sharing inefficiency
  • Патчі для кожної ОС окремо
💡 VM — золотий стандарт для production workloads де потрібна повна ізоляція та специфічна ОС.

Containers: namespace та cgroups


Linux Kernel
│
├── Namespace (ізоляція):
│     PID namespace    → процеси не бачать один одного
│     Network ns       → власний мережевий стек
│     Mount ns         → власна файлова система
│     User ns          → окремі UID/GID
│     IPC ns           → ізоляція IPC
│
└── cgroups (обмеження ресурсів):
      cpu.max          → ліміт CPU
      memory.max       → ліміт RAM
      blkio.weight     → пріоритет I/O
      cpuset.cpus      → прив'язати до конкретних ядер
💡 Container — це процес на хост-ОС з обмеженим "виглядом" через namespace та ресурсним лімітом через cgroups. Немає окремого kernel!

Коли що вибирати?


Потрібна специфічна ОС або Windows?
  └─► VM (EC2)

Довготривалий процес + повна ізоляція?
  └─► VM (EC2)

Мікросервіс, 12-factor app, швидкий деплой?
  └─► Container (ECS / EKS)

Бекенд-обробник подій, API, cron-задачі?
  └─► Serverless (Lambda)

ML training / GPU workloads?
  └─► VM (EC2 p3/p4 GPU instances)

На-edge / IoT?
  └─► Container (Greengrass) або Lambda@Edge
⚠️ У реальних системах всі три рівні часто використовуються разом.

Linux-first mindset у хмарі

📊 Статистика

  • ~90% публічних хмарних workloads — Linux
  • Всі AWS managed сервіси — Linux під капотом
  • Kubernetes nodes — Linux
  • Containers базуються на Linux kernel
  • Усі AWS-managed DB — Linux

🏆 Переваги Linux в хмарі

  • Open source = безкоштовно
  • Легкі AMI (Amazon Linux 2, Ubuntu)
  • Автоматизація: bash, Python
  • Security: менша attack surface
  • Package managers (apt, yum)
  • SSH — стандарт доступу
💡 "Linux-first" не означає "Linux завжди". Але означає: якщо можеш вибрати — вибирай Linux.

📋 Правила безпеки EC2


Інбаунд правила (Security Group):
  22/tcp  ← My IP (SSH)
  80/tcp  ← 0.0.0.0/0 (HTTP)
  443/tcp ← 0.0.0.0/0 (HTTPS)

Аутбаунд (default):
  All traffic → 0.0.0.0/0
  • Порти 0–1023: privileged (root)
  • Порти 1024+: unprivileged
  • Обмежуй доступ по IP!

Bash scripting: основи


#!/bin/bash
# Перший рядок = shebang (якій оболонці виконувати)

# Змінні
NAME="world"
echo "Hello, $NAME!"

COUNT=$(ls /etc | wc -l)   # command substitution
echo "Files in /etc: $COUNT"

# Умовні оператори
if [ -f "/etc/nginx/nginx.conf" ]; then
    echo "Nginx config exists"
elif [ -d "/etc/apache2" ]; then
    echo "Apache found"
else
    echo "No web server config"
fi

# Перевірки
[ -f file ]   # файл існує
[ -d dir ]    # директорія існує
[ -z "$VAR" ] # рядок пустий
[ $A -eq $B ] # числа рівні
[ $A -gt $B ] # більше ніж

SSH: підключення до EC2


# Підключення з key pair
ssh -i ~/.ssh/my-key.pem ec2-user@54.123.45.67

# Типові usernames:
#   Amazon Linux 2/2023:   ec2-user
#   Ubuntu:                ubuntu
#   RHEL/CentOS:           ec2-user або centos
#   Debian:                admin

# ~/.ssh/config для зручності
Host my-server
    HostName 54.123.45.67
    User ec2-user
    IdentityFile ~/.ssh/my-key.pem
    ServerAliveInterval 60

ssh my-server    # тепер просто так!

# SCP — копіювання файлів
scp -i my-key.pem file.txt ec2-user@54.123.45.67:/tmp/
scp -i my-key.pem -r ec2-user@54.123.45.67:/var/log/ ./logs/

# SSH tunneling (port forwarding)
ssh -L 8080:localhost:80 my-server   # local → remote
🔐 Ніколи не давай .pem файл нікому і не зберігай на публічних сховищах!

Immutable Infrastructure: концепція

🔧 Mutable Infrastructure


Сервер живе місяцями/роками
       ↓
ssh → apt upgrade → config edit
       ↓
git pull → restart nginx
       ↓
"snowflake server" — унікальний,
невідтворюваний стан
       ↓
Проблема: "Works on my server!"

🏗️ Immutable Infrastructure


AMI v1.0 (baked image)
    ↓  Deploy
EC2 instances (v1.0)
    ↓  New version needed
AMI v2.0 (new baked image)
    ↓  Deploy
EC2 instances (v2.0)  ← нові
    ↓
EC2 instances (v1.0)  ← terminated
💡 Ніколи не змінюй production сервер вручну. Зміни в code → новий AMI → deploy. Старий → terminate.

Stateless vs Stateful системи

🔄 Stateless

  • Сервер не зберігає стан між запитами
  • Будь-який сервер може обробити будь-який запит
  • Сесії/кеш → зовнішнє сховище (Redis, DynamoDB)
  • Легко масштабується горизонтально
  • Легко замінювати інстанси
✅ Cloud-native підхід

📌 Stateful

  • Сервер пам'ятає попередні запити
  • Сесії зберігаються локально
  • Файли / кеш на локальному диску
  • Sticky sessions (ALB)
  • Важко масштабувати та замінювати
⚠️ Ускладнює Auto Scaling
💡 Правило: HTTP сервери = stateless. БД, черги, кеш = stateful. Розділяй їх!

Проектування stateless сервісів


❌ Stateful (погано для cloud):            ✅ Stateless (cloud-native):

  Client → EC2-1                             Client → ALB
    EC2-1: session stored locally                   ↙    ↘
    Client → EC2-2? → "session not found"      EC2-1    EC2-2
                                              (обидва читають Redis)
                                                   ↓
                                                 Redis
                                               (ElastiCache)

  EC2-1 зберігає файли → /tmp/uploads         EC2-1 → S3 (спільне сховище)
  EC2-2 не бачить файлів                       EC2-2 → S3 (те саме)

  Конфіг: /etc/app/config.ini (локально)      Конфіг: AWS Parameter Store / Secrets Manager
💡 12-Factor App принцип: зберігай стан у зовнішніх сервісах (S3, Redis, RDS), а не на диску сервера.

AWS EC2: Introduction

🖥️ Що таке EC2?

  • Elastic Compute Cloud
  • VM у AWS (Nitro гіпервізор)
  • Вибір ОС через AMI
  • Вибір розміру через Instance Type
  • Запуск за секунди
  • Оплата за секунду (мінімум 60с)

⚙️ Компоненти при Launch

  • AMI — образ ОС
  • Instance Type — t3.micro, m6i.large...
  • Key Pair — для SSH доступу
  • Security Group — firewall правила
  • VPC/Subnet — мережева розміщення
  • Storage (EBS) — диск
  • User Data — скрипт при старті
💡 EC2 = найфундаментальніший AWS сервіс. Розуміння EC2 = фундамент для решти.

Spot Instances: переваги та обмеження

✅ Spot Instances підходять для

  • ML training (checkpoint + resume)
  • Batch обробка (відео, аналітика)
  • Big data / EMR кластери
  • CI/CD build runners
  • Stateless веб-серери (за ASG)
  • Rendering (3D, відео)

❌ Spot Instances НЕ підходять для

  • Production бази даних
  • Stateful сервіси
  • Критичні API (якщо без fallback)
  • Задачі без checkpoint/recovery
  • Long-running транзакції

Spot interruption: AWS надсилає:
  1. Interruption Notice  → 2 хвилини до termination
  2. Instance Metadata: /latest/meta-data/spot/termination-time
  → Твій код повинен перехопити і gracefully shutdown!

AMI: Amazon Machine Image


AMI містить:
  ├── Root volume snapshot (EBS або Instance Store)
  ├── Launch permissions (хто може запускати)

Auto Scaling Group (ASG)


                     ┌─────────────────────────────────┐
Traffic ──► ALB      │        Auto Scaling Group        │
            │        │                                  │
            ├──────► │  EC2 (AZ-a) ● ● ●               │
            ├──────► │  EC2 (AZ-b) ● ●                  │
            └──────► │  EC2 (AZ-c) ●                    │
                     │                                  │
                     │  Min: 2    Desired: 6    Max: 20  │
                     └─────────────────────────────────┘
                                    ↑
                          CloudWatch Alarm: CPU > 70%
                               → Scale Out (+2)
                          CloudWatch Alarm: CPU < 20%
                               → Scale In (-1)
💡 ASG завжди зберігає Desired capacity (заміняє terminated інстанси). Min = floor, Max = ceiling.

ASG Scaling Policies

🎯 Target Tracking

Підтримувати метрику на заданому рівні.


CPU = 60%
ALBRequestCount / target = 1000

✅ Найпростіший. Рекомендований.

📈 Step Scaling

Крок масштабування залежить від розміру відхилення.


CPU 70–80% → +1
CPU 80–90% → +2
CPU > 90%  → +4

ℹ️ Більш гнучкий

🗓️ Scheduled Scaling

За розкладом.


Пн-Пт 09:00 → min=5
Пн-Пт 18:00 → min=2
Чорна П'ятниця:
  Min=50, Max=100

⚠️ Треба знати патерн

💡 Cooldown period (default 300с) — пауза між scaling подіями, щоб уникнути oscillation.

Anti-Patterns: Що НЕ робити

❌ EC2 помилки

  • SSH на порт 22 відкритий для 0.0.0.0/0
  • Root EC2 user для застосунку
  • Hardcoded AWS credentials у коді
  • Один EC2 без ASG (SPOF)
  • Mutable сервери в production
  • Залишати зупинені EC2 (рахує EBS!)
  • t2.micro у production під навантаженням

❌ Linux помилки

  • Запускати застосунок від root
  • Зберігати secrets у /etc як plain text
  • Не налаштовувати firewall (iptables/nftables)
  • Ігнорувати security updates
  • Зберігати стан у /tmp (ephemeral!)
  • Не ротувати логи (переповнення диску)
  • Захардкодити паролі у bash скриптах
